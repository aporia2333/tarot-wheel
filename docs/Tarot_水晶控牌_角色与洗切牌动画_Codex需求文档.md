# 塔罗项目｜占卜师角色优化与水晶控牌洗切牌动画系统

> **用途**：直接交给 Codex，作为现有塔罗网页项目的开发任务说明。  
> **任务类型**：检查现有实现 → 制定与项目架构兼容的实施方案 → 修改代码与必要资源 → 验证结果。  
> **优先级**：自然的人物姿态、连贯的施法动作、真实可理解的洗牌/切牌、操作体验与性能之间的平衡。  
> **整体美术风格**：暗绿色与古金色、精致奇幻、低调魔法感、克制写实；不走夸张卡通或战斗法术风格。

---

## 0. 给 Codex 的执行总指令

请先**阅读项目代码和现有资源**，识别占卜师角色、塔罗牌、水晶球、桌面、牌阵选择页、洗牌/切牌页、抽牌流程及其关联状态。先确认项目使用的前端技术、图形渲染方式和资源组织，再基于本说明直接实施，而不是仅返回设计建议。

**不要破坏已经确定的产品规则**：

1. **洗牌与切牌位于同一场景/页面**，以角色对话和动画分阶段推进，禁止为两者切换到两个割裂的页面。
2. 通过**两轮占卜师对话**完成参数引导：第一轮决定洗牌次数，第二轮决定切牌次数；每轮均可让用户自行设定，或交由占卜师随机决定。
3. **没有“跳过”按钮**。正常流程需完整播放；必须提供技术上的取消/销毁/状态恢复能力，防止页面切换、组件卸载或异常造成卡死，但不要把它设计成面向用户的“跳过动画”功能。
4. 占卜师形象将来可以替换，所以**角色动作接口和角色资源解耦**，不能把所有行为写死在某一张人物图片上。
5. 洗牌/切牌必须改变**真实牌组顺序与抽牌数据**，不能只播放视觉特效；动画结果与业务状态应完全一致。
6. 保留现有牌阵、牌数、抽牌结果、正逆位、随机数等业务规则；如与当前实现发生冲突，保留原业务语义并在实施报告中说明。
7. 本文侧重**人物与洗切牌场景**；牌阵之书的现有 4×2 / 每页 8 项、两页布局等已定交互保持不变，不要借机重做无关页面。

若现有资源仅有一张包含头发、身体、袖子、双手与背景的平面图片，**不允许把简单平移/旋转整张图伪装成精细手臂动画**。须先评估可用资源：优先采用分层角色图、骨骼绑定、局部替换帧或独立手部层；素材不足时先实现可靠的牌与水晶动画，并说明人物动画所缺分层素材及临时方案，不能声称已实现真实关节动作。

## 1. 视觉定位与场景构图

### 1.1 保留角色识别特征

- 精致、柔和且略带神秘感的面容；不重新设计五官。
- 深绿色天鹅绒/布料、金色刺绣、白色荷叶边内搭。
- 月亮发饰、星星耳饰、长卷发等既有辨识度元素。
- 与哥特式书房、烛光、塔罗桌布、水晶球保持统一的光照与材质风格。
- 降低过度 Q 版化和塑料感，优先采用细腻的奇幻插画质感。

### 1.2 修正目前人物问题

现有立绘两侧袖子过于对称，呈近似封闭椭圆形；真实的肩、肘、腕结构难以辨认；双手放置也近似镜像，人物与桌面有“嵌在一起”的感觉。

**修正要求**：

- 肩部自然下沉，肩颈衔接顺畅；头部可小幅缩小，腰部不再过分收窄。
- 明确肩→上臂→肘→前臂→腕→手掌的结构，即便有宽袖遮挡也要符合解剖逻辑。
- 保留宽大宫廷袖，但袖口在桌面附近自然下垂，褶皱随肘腕动作产生合理变化；避免袖子形成左右对称的硬圆环。
- 双手位置采取**不对称构图**：画面左侧靠近水晶球的手为“供能/主控手”，画面右侧靠近牌堆的手为“引导手”。如项目采用镜像人物资源，应基于角色配置映射，而非硬编码 left/right 语义。
- 人物应像真实坐在桌前：身体与桌沿有明确前后遮挡关系，手腕能自然到达桌面，衣袖与桌布不穿插。
- 表情保持克制；加入轻微注视与自然浅笑，不要强制持续盯镜头。

### 1.3 场景元素位置

- 水晶球：保持画面左前侧，清楚可见，有独立动画层。
- 主牌区：桌面中前方，是悬浮、洗牌、切牌的视觉中心。
- 人物：上半身居中、手部能与水晶球及牌区形成合理的三角形视觉关系。
- 对话框/次数输入：避免覆盖人物脸、主要施法动作、牌堆轨迹和水晶球。
- 高层级牌：悬空时应正确遮挡背景物体，但不应无故穿过角色手掌、袖子或 UI。

## 2. 角色动作模型与资源规范

### 2.1 推荐分层

视当前技术条件尽量拆分：`body/torso`、`head`、`hair-front`、`hair-back`、`left-upper-arm`、`left-forearm`、`left-hand`、`right-upper-arm`、`right-forearm`、`right-hand`、`sleeves`、`accessories`、`shadow`。若使用 Live2D、Spine 或等价系统，遵循其骨骼/变形结构，不必机械按此命名。

关键约束：

- 转动中心必须设在解剖上合理的肩、肘、腕位置。
- 手指有至少若干预置姿态：放松、张开、托举、牵引、收势；无需首版制作复杂的每指独立物理模拟。
- 袖子随前臂联动，可使用变形贴图/局部序列帧避免硬片旋转。
- 可配置动作幅度，支持不同体型或新人物皮肤；替换素材不得改变业务流程。
- 面部表情、眨眼、视线与身体施法状态分开管理。

### 2.2 动作资产最低要求

**理想版**：分层立绘 + 2D 骨骼/局部变形 + 关键手势 + 表情/眼神层。  
**可接受初版**：保留静态躯干和头部，以独立的双手/前臂姿态帧配合牌和水晶特效，视觉过渡自然。  
**不合格版**：整张人物图片上下漂浮、两侧袖子同步伸缩、只有卡牌自己运动却声称人物在洗牌。

若缺少素材，请输出**具体素材清单**：需要哪几个透明图层/姿态、各自锚点与推荐画布尺寸、哪些必须重新绘制；不应直接破坏原立绘。

## 3. 行为与动画原则

1. **因果清楚**：人物眼神与手势先启动，水晶响应，牌随后运动；人物手势改变要与牌运动有时间关联。
2. **连续性**：场景中主牌堆的位置、速度、方向与遮挡关系跨阶段平顺；没有突变、瞬移或忽然换图。
3. **动作节制**：肩臂微动、腕指主导；不出现战斗施法式甩手、抖肩、大幅摇摆。
4. **牌是真实物体**：保持合理长宽比、牌背朝向、牌与牌的间距、边缘阴影；禁止无缘无故穿透、复制或消失。
5. **视觉特效是辅助**：以淡月白、暖金、浅青绿为主，细微光丝、薄雾与少量星尘；不要浓重霓虹光柱。
6. **动画逻辑可配置**：时间、缓动、次数、随机种子、运动轨迹、粒子强度支持集中修改。
7. **最终结果可重复验证**：开发测试中可以以固定 seed 重现相同的洗切牌和动画参数。

## 4. 完整时间线与分镜

下面时间只是**单次完整演出的建议值**，可按实际页面节奏与设备性能调整。交互等待用户输入的阶段**不计入**动画播放时长。

| 阶段 | 建议时长 | 人物行为 | 水晶/牌行为 | 结束条件 |
|---|---:|---|---|---|
| A. 待机 `idle` | 循环 | 呼吸、眨眼、轻微目光偏移 | 水晶微光，牌静止 | 进入流程 |
| B. 唤醒 `awakening` | 1.2–1.8s | 主控手抬起、指尖张开、视线转向水晶 | 水晶光雾渐亮，牌边缘回应 | 唤醒完成 |
| C. 悬浮 `levitating` | 1.5–2.2s | 主控手托举，引导手指向牌区 | 牌先整体离桌，再升空，最后展开 | 悬浮稳定 |
| D. 空中洗牌 `shuffling` | 每轮约 2–3s | 主控手稳能量，引导手做弧线牵引 | 分组→穿插→重排→聚拢 | 当前回合完成 |
| E. 洗牌收势 `shuffleHold` | 0.3–0.7s | 手势微收、目光停留 | 牌悬浮稳定，等待切牌参数 | 显示第二轮对话 |
| F. 魔法切牌 `cutting` | 每次约 1.5–2.2s | 引导手横向分割/交换、主控手稳牌 | 牌堆切分→组移→顺序交换→合并 | 当前回合完成 |
| G. 归位 `settling` | 1.0–1.5s | 双手逐步放松、回到桌前 | 牌堆对齐并柔和落桌，水晶降亮 | 全部动画完成 |
| H. 待抽 `readyToDraw` | 持续 | 轻微邀请姿态 | 牌区可交互，光效回待机 | 用户开始抽牌 |

### 4.1 A — 待机：有生命感但不干扰

- 胸肩非常轻微的呼吸位移；自然眨眼，间隔略随机。
- 发丝、耳饰只有极低振幅摆动，避免持续像被风吹。
- 水晶内部低速雾纹与点状反射；桌面牌静止。
- 移动端或低性能模式可简化到眨眼、水晶低频亮度变化。

### 4.2 B — 唤醒：先角色、后水晶、再牌

按相对进度控制：

1. **0–25%**：眼神从用户转向水晶，主控手手腕缓慢抬起；身体微前倾。
2. **20–60%**：主控手食指、中指轻张；水晶内部浮现细微旋涡，亮度自然递增。
3. **55–90%**：引导手转向主牌区；牌边缘闪出低强度金光，牌堆微震，桌面投影仍真实。
4. **90–100%**：短暂停顿，给悬浮建立蓄势感。

### 4.3 C — 悬浮：从完整牌堆到空中扇面

1. **起升**：牌堆作为一个整体先离桌极小距离；牌下方接触阴影柔化。
2. **抬升**：整体缓慢升到清晰可见的桌面上方；牌的阴影与高度对应变化。
3. **展牌**：按索引逐渐错开成浅弧形扇面，中心略高、左右延展；牌与牌不重叠到无法辨认。
4. **稳定**：所有牌以极低振幅浮动，并保持可预期的排列方向。

**优先实现弧形扇面**；若空间允许可加入少量旋转/深度差，而不是首版追求复杂环形轨道。

### 4.4 D — 洗牌：每轮必须发生真实重排

每轮分三个连续子段：

- **D1 分组展开（约 25%）**：牌在空中分成 2 或 3 个互斥子组，沿不同弧线展开；手势由稳态转向牵引。
- **D2 交错穿插（约 50%）**：子组遵循可读轨迹有节奏地交叉，保持牌间距离、正确 z-order；不要只是整副牌无意义地公转。
- **D3 聚拢重组（约 25%）**：新顺序的牌沿收敛路径汇成牌堆/窄扇面；手部自然收势，水晶亮度小幅回落。

建议实现**2–3 种同一语义下的轨迹变体**：双组交错、三组依次穿插、反向弧线重排。变化可随机，但每种都必须更新数据中的牌序。

多轮播放：第一轮演示完整，中间轮可适当加快或缩短停顿，最后一轮完整收势。不能因为压缩视觉时长而少做实际洗牌次数。

### 4.5 E — 洗后悬停及第二轮引导

- 洗牌完成时，牌应保持稳定悬浮，避免先落桌再无故升空。
- 占卜师收敛动作但仍维持控制姿态；水晶维持柔和持续发光。
- **此时显示第二轮占卜师对话**，引导用户设置切牌次数或交由占卜师随机；用户确认后进入切牌。
- 等待过程中不要持续高频空转，以免造成等待焦虑与性能浪费。

### 4.6 F — 切牌：切分与重组可被观察

对一次典型二段切牌：

1. 悬浮牌堆在固定位置停稳。
2. 按真实卡牌索引 `cutIndex` 分成 A、B 两段；两段沿水平与纵深方向拉开足够间隔。
3. 引导手做温和的侧向划动；A、B 沿不碰撞的弧形路径互换上下先后位置。
4. 两组重新上下叠合并自动对齐，形成 `B + A` 的新顺序。
5. 主控手保持支撑，牌堆短暂停顿再进入下一轮。

三段变体可为 `A+B+C → B+C+A` 或 `C+A+B`，但**分组和新顺序必须由同一份真实数据定义**。用户设置的是**切牌次数**，不是必然切成对应数量的段；每一轮可为两段或三段，依实际规则决定。

### 4.7 G — 归位：进入抽牌准备

- 完成最后一次切牌后，牌堆保留悬停 0.2–0.4 秒以突出仪式完成。
- 水晶亮度自然降低；双手顺着上一手势缓慢放松。
- 牌堆平稳下降到桌面指定位置，逐张对齐，接触阴影恢复。
- 使用短促且轻柔的完成反馈，禁止高强度闪屏、突然爆炸粒子或重物砸落感。
- 角色回到待机姿态，系统进入 `readyToDraw`，继续原项目抽牌流程。

## 5. 人物动作细则

### 5.1 眼睛与头部

- `idle`：偶尔眨眼，眼神平静。
- `awakening`：先看向水晶，微低头。
- `levitating`：视线移向升起的牌堆。
- `shuffling`：眼神跟随当前主牌组，头部小幅转动。
- `cutting`：看向正在交换的两组/三组牌。
- `settling`：视线跟随落桌，然后自然回望用户。

不使用持续晃头、机械固定速度来回看、突然瞬间切换眼睛方向。

### 5.2 上身与肩膀

- 肩颈始终放松，动作中心在前臂/手腕/手指。
- 手势带动轻微肩带与躯干变化，但位移幅度要小。
- 施法过程中身体重心保持稳定；角色像掌握力量的占卜师，而不是在表演夸张魔术。

### 5.3 主控手（水晶侧）

- 待机：手腕自然松弛，靠近水晶但不穿插水晶或桌面。
- 唤醒：手掌微张、指尖抬起。
- 悬浮：手掌转为轻托姿态，与牌堆上升同步。
- 洗牌：基本稳定，允许极细微的腕部旋动来表达能量维持。
- 切牌：轻微收紧指尖，体现牌组受约束。
- 归位：缓慢下降、手指放松、回到起始区域。

### 5.4 引导手（牌区侧）

- 待机：自然靠近桌面中央牌区。
- 唤醒：掌心/指尖逐步朝向牌堆。
- 悬浮：手掌缓慢朝上引导，领先卡牌位移少许。
- 洗牌：用小幅侧向弧线、指向与轻旋手腕表现“分组—交错—聚拢”。
- 切牌：明确做出“分开—交换—收合”的三段手势。
- 归位：手指回收、手臂自然下落，结束时不必左右对称。

### 5.5 动作衔接

- 动作不应每阶段重置到原位再重新起势。
- 关键姿态之间要有合理插值和停顿，不允许肩、肘、腕突然跳帧。
- 关节动作不应导致袖子或手背突然变形、左右手穿插。
- 首轮洗牌到下一轮洗牌沿用当前手势状态；洗牌转切牌以短暂停顿连接。

## 6. 水晶球与魔法特效

### 6.1 水晶状态

| 状态 | 发光 | 内部动态 | 与牌联系 |
|---|---|---|---|
| 待机 | 极低 | 缓慢雾纹 | 无 |
| 唤醒 | 逐渐增强 | 柔和旋涡、几点星尘 | 细微响应 |
| 悬浮 | 稳定中高 | 轻流动 | 微弱光丝/空气涟漪 |
| 洗牌/切牌 | 随动作脉冲但不闪烁 | 有节奏流转 | 和关键移动同步 |
| 归位 | 渐弱 | 恢复缓速 | 逐步消散 |

### 6.2 特效边界

- 避免粗实能量光束、廉价光圈、频闪、满屏粒子。
- 尽量借助折射、高光、局部渐亮、稀疏光点与淡光丝表现魔力。
- 光效不遮住牌背图案、手部关键姿态、角色面部和界面文字。
- 所有粒子数量、模糊半径与亮度可配置，并可在低性能模式关闭。

## 7. 两轮对话和交互流程（必须保持）

**场景原则**：洗牌和切牌始终在同一个桌前场景，故事由占卜师对话推进；不要出现单独“洗牌页面”跳到“切牌页面”的割裂感。

### 第一轮对话：决定洗牌次数

示例话术：

> 「先让水晶感应你的心绪。你想亲自决定洗牌次数，还是交给我？」

交互提供：

- **自行设定**：显示洗牌次数控件，并在合理范围内校验；如项目已有次数上限，以既有规则为准；没有约束可暂用 1–7 次作为可配置默认值。
- **交给占卜师**：由项目的随机模块决定洗牌次数，并在内部记录最后采用的值。
- **确认**：锁定参数，进入唤醒→悬浮→洗牌。动画期间防止重复提交。

### 第二轮对话：决定切牌次数

第一轮动画结束，悬浮牌堆稳定后显示：

> 「牌已回应水晶。接下来，要由你决定切牌次数，还是让我为你完成？」

交互提供：

- **自行设定**：显示切牌次数控件；如没有既定规则，可暂用 1–5 次作为可配置默认值。
- **交给占卜师**：随机生成次数，并记录实际值。
- **确认**：锁定参数，执行切牌→归位→待抽。

完成话术：

> 「仪式已经完成。现在，请抽出属于你的答案。」

**注意**：

- “自行设定”和“交给占卜师”是两种互斥选择，不强制用户两轮选择同一模式。
- 不提供跳过按钮；等待用户决定时不得自行越过第二轮。
- 用户开始仪式后，不再要求重复点多次“继续”才能播放同一轮动画。
- 已有 UI 的视觉语言应与当前项目统一：古典、清晰、自然嵌入场景，不能突然切换现代控制面板风格。
- 支持键盘操作和屏幕阅读器的状态提示；减少动作模式下仍可完成所有操作。

## 8. 核心业务逻辑：牌序必须和画面一致

动画不是随机装饰。无论随机模式还是自行设定，最终都必须操作**同一份实际卡组状态**：

1. 从当前牌组数据生成有唯一 `cardId` 的卡片集合；不要假设所有皮肤或玩法都固定 78 张，如有既有配置使用实际卡数。
2. 每次洗牌使用项目已有的、可验证的洗牌算法或合适的等概率重排方法（如 Fisher–Yates）；一次动画回合对应一次真实洗牌操作。
3. 动画中各卡片视觉实例必须持续绑定对应 `cardId`，不可只随机更换牌面贴图。
4. 切牌必须按实际 `cutIndex` 拆分数组并重组，例如 `deck = deck.slice(k).concat(deck.slice(0,k))`；三段切牌按定义好的段索引与顺序重组。
5. 每个动画阶段应采用**先计算操作计划、再驱动视觉执行、最后安全提交/确认状态**的流程；避免一半卡牌已移动但底层状态未同步。
6. 在用户离开页面、操作被取消或动画异常时，不能丢失牌或产生重复卡；可回滚到开始状态，或按既定事务语义完成并提交，但必须有统一策略。
7. 洗牌/切牌次数精确执行，不能因为多轮加速而减少实际操作。
8. 随机模式的随机来源与种子策略遵循项目现有实现；为测试提供固定 seed 的可复现场景，但生产环境不要固定 seed。
9. 如果项目支持逆位、抽牌前反转、正逆位独立随机或特殊牌背状态，保持原规则；普通洗牌/切牌动画不应擅自更改逆位概率。
10. 洗牌后切牌所操作的必须是洗牌后的最新卡组，抽牌再使用切牌后的最终卡组。

**验收测试**：每轮前后卡片 `cardId` 的多重集合完全相等；卡数不变、没有重复或丢牌；洗/切牌次数与记录一致；抽牌结果来自最终牌组。

## 9. 前端架构与动画状态机

建议以项目现有框架为准，不强行引入依赖。可使用 CSS Transform、Web Animations API、现有动画库或 Canvas/WebGL；**优先复用已有技术栈**。复杂分层角色如需额外运行时，请先确认已有资源和打包条件再决定。

### 9.1 状态划分

建议区分“交互流程阶段”和“表演动画状态”：

- `awaitShuffleConfig`：第一轮对话，等待设置洗牌。
- `awakening`
- `levitating`
- `shuffling`
- `awaitCutConfig`：悬浮等待第二轮对话。
- `cutting`
- `settling`
- `readyToDraw`

另设角色细分动画状态，如 `gaze`, `handPose`, `breathing`, `crystalIntensity`，不要依靠一大堆互斥布尔值管理所有动画。

### 9.2 动作计划示例（概念级接口）

```ts
interface RitualConfig {
  shuffle: { mode: 'manual' | 'oracle'; count: number };
  cut: { mode: 'manual' | 'oracle'; count: number };
  seed?: number; // 仅复现/测试时可选
}

type RitualPhase =
  | 'awaitShuffleConfig'
  | 'awakening'
  | 'levitating'
  | 'shuffling'
  | 'awaitCutConfig'
  | 'cutting'
  | 'settling'
  | 'readyToDraw';

interface CardMotionPlan {
  cardId: string;
  from: { x: number; y: number; z: number; rotate: number };
  to: { x: number; y: number; z: number; rotate: number };
  durationMs: number;
  delayMs: number;
}
```

这只是建议结构，**不要为迎合示例而改坏现有类型系统**。

### 9.3 参数集中配置

集中维护：

- 动画阶段时长、首轮/中间轮/末轮的不同节奏。
- 悬浮高度、扇面宽度、牌间距、牌的 z-order 与阴影强度。
- 分组数量、交叉幅度、切牌横向位移与安全间隔。
- 手腕转角、肩臂微动幅度、手指姿态、眨眼节奏。
- 水晶亮度曲线、雾纹速度、光丝长度、粒子数量。
- 可减少动作与低性能两种简化强度。

### 9.4 组件划分建议

可按项目结构拆分，但职责要明确：

- `TarotRitualScene`：角色/桌面/水晶/牌的整体空间与层级。
- `TarotReaderActor`：角色表情、视线、骨骼或姿态资产控制。
- `CrystalEffect`：水晶各状态光效。
- `FloatingDeck`：牌的独立位置、遮挡、动画序列。
- `RitualDialogue`：两轮对话与次数选择。
- `RitualController`：状态机、回合次数、动作计划与回调。
- `DeckEngine` 或现有模块：纯数据的洗牌/切牌与抽牌状态。

不要出现两个各自维护不同牌序的“视觉卡组”与“真实卡组”。

## 10. 体验、响应式与性能要求

- **桌面优先**：在 1920×1080 和常见较窄视窗里，人物、牌、水晶及控制区域都应完整呈现，不遮住页头与主要导航。
- **移动端**：缩放人物、收窄悬浮扇面轨迹及位移，保证操作控件可点且画面不越界。
- 使用 transform/opacity 等友好的动画属性；避免逐帧触发布局/大量高成本模糊。
- 尽量避免同时存在大量完整分辨率纹理、复杂粒子与昂贵过滤器。
- 重复执行仪式不应产生额外定时器、事件监听器或未释放纹理。
- 页面切换、卸载、失焦、路由变化等必须进行动画清理；禁止因 Promise 永不结束或事件丢失而卡住。
- 支持 `prefers-reduced-motion`：保留**洗牌/切牌真实业务逻辑与状态提示**，将飞行轨迹、闪光和旋转简化为短过渡或直接就位；不要把减少动作理解为跳过业务步骤。
- 如浏览器缺少悬停交互，触屏也可以完整设置次数并继续流程。
- 有合适的音效资源时可以使用极轻微纸牌/玻璃共鸣音；没有则不要为了音效额外引入不稳定依赖，默认无声可运行。

## 11. 实施顺序与优先级

### P0 — 先保证“真的能用”

1. 检查并确认现有牌序、洗切次数、抽牌流程。
2. 建立统一状态机和参数控制（两轮对话、同屏、无跳过）。
3. 真实洗牌/切牌与 `cardId` 动画映射，确保不丢牌不复制。
4. 实现稳定可读的悬浮、交错洗牌、分段切牌、归位完整闭环。
5. 解决屏幕布局、遮挡、重入、异常清理与构建报错。

### P1 — 人物与视觉连贯性

1. 检查人物资源的分层/绑定可行性，列出并修正当前姿态缺陷。
2. 加入眼神、手腕、手指、肩部的阶段动作与过渡。
3. 加入水晶不同状态、细光丝、自然投影与袖子联动。
4. 优化角色动作提前量，使手势与牌的运动有因果联系。

### P2 — 可扩展与精修

1. 实现 2–3 种洗牌轨迹变体与切牌组合。
2. 角色皮肤替换时复用同一套动作接口。
3. 性能自适应、低动作模式与细节调参。
4. 加入开发时的固定 seed 回放与必要的动作状态调试面板（仅开发环境）。

如果现有资源不支持真正的手臂关节动作，P0 仍须完成，P1 列明所需美术资源并落地能够可靠实现的部分，不要使用粗糙变形凑合。

## 12. 验收标准

### 12.1 外观与角色

- [ ] 角色身份特征和深绿金色的美术语言保留。

- [ ] 没有用整张图片机械漂浮冒充细腻人体动作。

### 12.2 动作可读性

- [ ] 有唤醒→悬浮→洗牌→切牌→归位→抽牌的完整仪式。
- [ ] 卡牌运动从静止开始、回到稳定结束，关键阶段无跳变。
- [ ] 洗牌能看出分组、交错和聚拢；切牌能看出切分、交换和合并。
- [ ] 卡牌数量、身份及最终顺序与数据逻辑一致。
- [ ] 水晶效果有层级与节奏，不遮挡重要操作。

### 12.3 产品交互

- [ ] 洗牌与切牌同一场景，正好两轮参数引导对话。
- [ ] 每轮均支持用户指定或占卜师随机，且模式可独立选择。
- [ ] 没有“跳过”按钮，没有重复点击或多次触发问题。
- [ ] 流程完成能够进入现有抽牌与后续解读。
- [ ] 页面卸载/异常恢复正常，低动作模式能完成全流程。

### 12.4 工程质量

- [ ] 代码通过项目原有 lint/typecheck/build/test（以实际提供的命令为准）。
- [ ] 新增动画资源/组件清晰组织，关键参数集中可调。
- [ ] 牌序变化有测试覆盖，至少覆盖多轮洗牌、两段/三段切牌、固定 seed、重复进入和中途退出。
- [ ] 不改变牌阵之书与其他既定页面的业务规则。
